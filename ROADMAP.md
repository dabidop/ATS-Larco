## Alcance que debe respetarse

- **Se conserva:** NestJS 11 + PostgreSQL 16, React 19/Vite, solicitudes, candidatos/CV, embudo de cinco fases, entrevistas, usuarios, departamentos, dashboard y auditoría. El esquema tiene migraciones `001–022`; `009` impone **una sola postulación total por candidato**; `020` retira verificaciones, `021` exige clasificación/asignación de área previa para candidatos sin área y `022` ajusta la FK a `ON DELETE RESTRICT`. No cambiar esta regla por iniciativa del agente.
- **No confundir dos significados de «verificación automatizada»:** las comprobaciones automáticas **del aplicativo** (tests, validaciones, permisos, integridad y CI: T01, T03, T04, T13–T16) **no son** verificaciones de antecedentes de personas. Por separado, el punto D de `ALCANCE.pdf` sí menciona consultas de antecedentes con Playwright; `PROJECT_CONTEXT.md` registra la decisión posterior de hacer antecedentes/proveedor fuera del ATS. El código actual no tiene esos módulos, worker, rutas ni UI y `020_retirar_verificaciones.ts` retira su esquema. No reconstruir consultas externas por confundirlas con pruebas automáticas del aplicativo. Las columnas del embudo siguen siendo fases manuales.
- **No rehacer:** `AuthGuard` ya consulta rol/sesión actuales en BD fuera de test; `ArchivosCvService.descargar` ya verifica el SHA-256 del CV; código REQ, reglas de cupo, descarte e historial existen. Corregir solo si una prueba concreta demuestra un defecto.
- **Fuera de este plan:** SSO, ERP/nómina, portal de candidatos, microservicios, nuevas integraciones y formularios de aprobación externos. Si un dato funcional imprescindible no está definido, anotar la decisión concreta que falta; continuar con otra tarea ejecutable. No bloquear todo el proyecto por documentación ceremonial.

## Cómo continuar en otra sesión

1. Leer `PROJECT_CONTEXT.md` y este archivo; ejecutar `git status --short`. Hay cambios previos sin confirmar, incluidas las migraciones `016–022`; no descartarlos. Elegir **la primera tarea pendiente cuyas dependencias estén resueltas**, salvo que el usuario pida otra.
2. Trabajar solo los archivos de esa tarea; usar datos sintéticos. Nunca probar contra `hojasdevida/`, copiar `.env` ni ejecutar migraciones/rollback en una BD con datos sin identificarla y asegurar su respaldo. `020` elimina tablas/tipos de verificaciones y no debe revertirse para recuperar datos; `021` no puede aplicarse hasta clasificar manualmente los candidatos sin área; `022` solo se revierte después de retirar 021 en un entorno controlado. **No ejecutar rollbacks para probarlos.**
3. Antes de marcar `[x]`, anotar en la misma tarea: fecha, archivos, verificación ejecutada y resultado. Si no se ejecutó, mantener `[ ]`. Tests con dobles de BD no cuentan como prueba PostgreSQL real; Vitest de componentes no cuenta como E2E de navegador.
4. Prioridades: **C** bloquea el uso productivo con datos reales; **A** cierra una brecha del alcance/flujo; **M** mejora condicionada a una necesidad comprobada. Tareas C pueden prepararse en paralelo, pero el orden de despliegue es obligatorio.
