## 1. Propósito y alcance

ATS interno de LARCO para Gestión Humana: registrar solicitudes de personal, mantener una base de candidatos y CV, vincular candidatos a vacantes, mover postulaciones por un embudo de cinco fases, agendar entrevistas, seguir decisiones y consultar una bitácora. Es un **piloto/MVP avanzado**, no un producto listo para operar con datos reales en producción. El alcance inicial está en `ALCANCE.pdf`; la planificación y los criterios de producción están en `docs/PLAN-PRODUCCION-ATS.md`, `docs/terminar.md` y `docs/tareas-para-produccion.txt`. Estos últimos contienen afirmaciones históricas y no deben reintroducir verificaciones retiradas.

No hay portal del candidato, app móvil, multitenancy, SSO ni integración con nómina/ERP. Los indicadores ejecutivos y las notificaciones son aspiraciones, no capacidades actuales.

El servidor, no los predicados de `lib/rbac.ts`, es la fuente de permisos.

## 4. Modelo de datos (estado definido por migraciones)

La existencia de estas definiciones **no confirma su aplicación a una BD concreta**. Resumen de claves, relaciones e invariantes:

- `roles(id, code UNIQUE, name)` ← `users(role_id)`; `users(id, email UNIQUE, password_hash, full_name, active, jefatura, …)`. `002` siembra tres roles (`admin_rrhh`, `analista_seleccion`, `lider_area`) y la cuenta admin; `008` agrega superusuario IT; `016` repara el rol de la cuenta semilla si no existe ningún IT activo (y evita dejar el sistema sin IT en `down`).
- `audit_log(bigserial, table_name, record_id, action, old_data/new_data JSONB, changed_by → users SET NULL, created_at)`; triggers de BD registran cambios; otro trigger impide UPDATE/DELETE directos. `004` mejora atribución del actor con GUC transaccional `app.current_user_id`; `011` amplía auditoría de DELETE para candidatos. No equivale a una bitácora legal completa de accesos/descargas.
- `requerimientos(id, code UNIQUE, estado ENUM, created_by → users, titulo, jefatura, numero_plazas, ubicacion, fecha_requerida, perfil_profesional, experiencia_requerida, nivel_educacion, conocimientos text[], habilidades text[], salarios, contrato, jornada, justificacion, urgencia, modalidad, departamento_id → departamentos SET NULL, motivo_rechazo, motivo_cierre, resultado_cierre, timestamps)`. Estados: `pendiente`, `aprobado`, `en_proceso`, `cerrado`, `rechazado`, `exitoso` (agregado en `009`; su `down` no puede retirar el valor ENUM). `codigo_sequences(anio PK, ultimo)` para código atómico. CHECK de plazas, salarios, motivo y campos funcionales de escrituras nuevas (`013 NOT VALID`: los datos históricos pueden incumplirlo).
- `departamentos(id, nombre UNIQUE, coordinador, timestamps)`; se siembran ocho áreas en `009` y `012` retira valores demo heredados.
- `candidatos(id, nombres, apellidos, email UNIQUE cuando no nulo, cedula_cifrada, cedula_hash UNIQUE si presente, telefono_cifrada, ciudad, departamento_id → departamentos SET NULL, cargo_actual, expectativa_salarial, disponibilidad, notas, created_by → users, timestamps)`. `010` hace opcional la cédula (ver valores nulos antes de asumirla obligatoria). Cédula/teléfono: AES-256-CBC formato `v1`, IV aleatorio; hash de búsqueda HMAC-SHA-256 con clave separada.
- `archivos_cv(id, candidato_id → candidatos CASCADE, sha256, filename_original, mime_type, size_bytes, created_by → users, created_at)`: `UNIQUE(candidato_id, sha256)`; blob en `<UPLOAD_DIR>/<sha256>`, compartible por metadatos de distintos candidatos.
- `postulaciones(id, candidato_id → candidatos CASCADE, requerimiento_id → requerimientos CASCADE, fase, estado, motivo_descarte, created_by → users, timestamps)`. Fases `preseleccion → antecedentes → entrevistas → proveedor_externo → contratacion`; estados `activa`, `contratado`, `descartado`. CHECK: contratado ⇔ fase contratación; descarte exige motivo. `009` cambia la unicidad inicial (candidato, requerimiento) por candidato únicamente y elimina duplicados históricos conservando la postulación más antigua. `entrevistas(id, postulacion_id → postulaciones CASCADE, fecha, hora, tipo, entrevistador, estado [agendada/realizada/cancelada], notas, created_by, timestamps)`.
- `auth_sessions(id, user_id → users CASCADE, refresh_token_hash UNIQUE, created_at, last_used_at, expires_at, revoked_at, user_agent, ip_address)` (`014`) y `auth_session_refresh_tokens(id, session_id → auth_sessions CASCADE, token_hash UNIQUE, issued_at, used_at, replaced_by_hash)` (`015`). Solo hashes SHA-256 de refresh, nunca el token claro en BD.

## 6. Autenticación, autorización y datos personales

- Roles: `admin_rrhh`, `analista_seleccion`, `lider_area`, `superusuario` (IT hereda administración RRHH y gestiona cuentas/bitácora). Guards globales en orden `AuthGuard` → `RolesGuard` → `ThrottlerGuard`; 100 solicitudes/minuto por IP y login 5/minuto. La API verifica JWT y en entorno no-test consulta sesión no revocada/usuario activo; cookies para access/refresh `HttpOnly`, `SameSite=Strict`, `Secure` en producción, CSRF double-submit para escrituras con cookie. Refresh público necesita cookie + CSRF y rota el token; access 15 minutos por defecto, refresh 7 días. Existe `JWT_TTL_HOURS=24` legado: no confundirlo con el access actual. Las pruebas `NODE_ENV=test` omiten verificaciones de sesión/CSRF del guard y desactivan rate limit general: no extrapolar resultados a producción.
- El frontend guarda en `localStorage` (`ats.sesion.v2`) el marcador `cookie` y datos del usuario; `lib/api.ts` reintenta una vez con refresh ante 401. Compatibilidad con Bearer en cliente/guard; revisar seguridad de esa vía antes de producción. La UI oculta acciones mediante `lib/rbac.ts`, pero **no autoriza**.
- Para cédula/teléfono: `CryptoService` AES-256-CBC y clave `CRYPTO_KEY_BASE64`; admite clave anterior opcional; `SearchHashService` requiere `CEDULA_SEARCH_KEY` para HMAC de búsqueda exacta. Los CV están **sin cifrar en disco**.
- Permisos de acceso a PII: consulta de candidatos e historial por cualquier autenticado. Esto **no** reemplaza consentimiento ni matriz de necesidad de conocer. El `DELETE` físico de candidato sin postulación está implementado; aún no hay derecho de supresión/anonimización coordinada.

## 8. Deuda técnica, riesgos y trabajo pendiente

**Bloqueantes para producción:** política de acceso a PII, retención y derechos de titulares, cifrar/proteger CV, antivirus, backups+restore probado, TLS y despliegue productivo reproducible, secretos separados, CI obligatorio y UAT de GH. `docker-compose.dev.yml` es **solo desarrollo**; no hay `docker-compose.prod.yml` ni `.github/workflows/` en el árbol revisado. No hay prueba E2E real del navegador de este ATS ni monitoreo/alertas.

**Producto:** importación con cola persistente y revisión humana, extracción de habilidades y OCR/fallback; reportes de conversión/tiempos y exportación; evaluaciones y recordatorios; catálogo administrable; plantillas/SLA; notificaciones. Ver `docs/tareas-para-produccion.txt` para backlog histórico, **no copiar literalmente sus estados**: sus tareas de verificaciones están retiradas. Confirmar con producto si se conserva la restricción de una sola postulación por candidato.

**Consistencia y escalado:** `packages/shared` es stub, contratos duplicados, no OpenAPI; revisar transacciones multinivel candidato/CV/importación, paginación y EXPLAIN con datos reales, concurrencia de altas y cierre, recuperación de ficheros huérfanos. `009` borra postulaciones duplicadas históricas al migrar; no ejecutar migraciones/rollback a ciegas sobre datos reales. `013` deja restricciones `NOT VALID` para históricos; estado de saneamiento desconocido. `016 down` puede conservar rol del último superusuario por diseño, y `009 down` deja valor `exitoso` del ENUM: reversibilidad limitada.

**Seguridad a comprobar:** `AuthGuard` valida la sesión y relee el rol efectivo desde `users` en cada solicitud protegida. Revisar refresh paralelo y rotación, snapshots de `audit_log`, exposición de cédula/teléfono a todos los roles y transporte/devolución de PII. Los tests e2e con dobles no demuestran comportamiento de la BD real. No afirmar que haya un fallo reproducido en producción a partir de estas observaciones estáticas.

**Próximos pasos recomendados (en orden):** (1) acordar con GH la regla de unicidad de postulaciones; (2) convertir importación a flujo confirmable y resistente a fallos; (3) desplegar staging con CI, TLS, backup/restore y UAT; (4) completar indicadores y mejoras operativas acordadas. No reintroducir verificaciones externas ni tratar el backlog anterior como alcance aprobado.

## 9. Arranque y desarrollo

1. Requisitos: Node compatible con el lockfile (declarado `>=24`), pnpm 12.14.0/Corepack, Docker para PostgreSQL 16. `pnpm install` desde raíz; `pnpm-workspace.yaml` permite builds de `@swc/core` y `esbuild`, bloquea `canvas` opcional de pdfjs.
2. Crear `.env` local **a partir de** `.env.example` sin versionarlo. Configurar `DATABASE_URL`, `JWT_SECRET` (mín. 32 caracteres), `CRYPTO_KEY_BASE64` y `CEDULA_SEARCH_KEY` (32 bytes aleatorios en base64), y `ADMIN_INITIAL_PASSWORD` + `SUPER_INITIAL_PASSWORD` para seeds 002/008 en una BD nueva. No publicar valores de `.env`.
3. Local: `pnpm db:up`; `pnpm --filter @ats/api db:migrate` (ejecuta node-pg-migrate con `.env` raíz; requiere DB disponible); `pnpm dev` (compila shared y arranca watchers). Web `http://localhost:5173`, API `http://localhost:3000/api`, proxy `/api` configurado en `apps/web/vite.config.ts`. Alternativa contenedores: `pnpm compose:up` levanta DB/API/web; **comprobar que las migraciones se aplicaron**, Compose no declara un servicio de migración. Ajustar entorno y directorio de uploads al contenedor.
4. Verificación de cambios de desarrollo: `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test` o pruebas puntuales `pnpm -C apps/api exec vitest run test/<suite>` / `pnpm -C apps/web test`; `pnpm build` solo cuando corresponda. Migraciones nuevas deben tener `up/down` razonados y pruebas sobre PostgreSQL antes de despliegue. No usar `.env` con credenciales reales en tests.

**Qué se verificó para este documento:** lectura de manifiestos/configuración, rutas/controladores, servicios clave, esquema y migraciones, interfaz, pruebas locales y documentación histórica. La migración `020` fue aplicada en `ats_dev`; typecheck y suites API/web pasaron. Otros entornos, navegador productivo y despliegue siguen sin validarse.
