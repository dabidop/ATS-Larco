1. STACK Y ARQUITECTURA
================================================================================

  API (apps/api)
    NestJS 11 + TypeScript estricto (Node >=20, engines del monorepo).
    Validación de DTO con class-validator (whitelist + forbidNonWhitelisted,
    mensajes en español); zod SOLO valida variables de entorno
    (src/config/env.validation.ts).
    Persistencia: pool `pg` global (DatabaseService) para casi todos los
    módulos + DataSource de TypeORM SOLO en el módulo requerimientos.
    Migraciones: node-pg-migrate con archivos TS en apps/api/db/migrations
     (001–012) — NO hay Prisma en el proyecto.
    Seguridad: helmet, CORS endurecido, Throttler global (100 peticiones/
    minuto por IP) y @Throttle(5/min) en login; nestjs-pino (logging).
    CV: multer en memoria, 5 MB máx., tipo real por MAGIC BYTES (PDF/DOC/
    DOCX/RTF), dedup por SHA-256.
    PDFs de HVs (Etapa 9): pdfjs-dist 3.11.174 (build legacy CJS) para
    extraer texto en la importación masiva. pdf-parse fue RECHAZADO: traía
    canvas (dependencia nativa); en pnpm-workspace.yaml está
    allowBuilds.canvas: false. NO hay generación de PDFs ni módulo de
    reportes en esta versión.

  Web (apps/web)
    React 19 + Vite 8 + TypeScript estricto + Tailwind CSS 4.
    React Router 7 · Zustand 5 (sesion, tablero) · dnd-kit (Kanban).
    Fetch tipado propio en lib/api.ts (solicitud<T>): SIN TanStack Query,
    SIN react-hook-form y SIN zod en el frontend (validación manual con
    mensajes en español).
    Vitest 5 + Testing Library: 110 pruebas (16 archivos).

  BD
    PostgreSQL 16 (imagen postgres:16-alpine) con migraciones versionadas
    (node-pg-migrate) y la filosofía «la base de datos manda»: CHECKs,
    triggers y unicidad viven en el esquema, no solo en la aplicación.

  Infraestructura
    docker-compose.dev.yml (db + api + web con bind mounts y watch; el flag
    -f es obligatorio). NO hay docker-compose.prod.yml ni CI/CD en el repo.

  Tests verificados (27/10/2026): API 395/395 (32 ficheros, incluye 230
  e2e contra BD real) · Web 110/110 · shared 2/2 · gates (typecheck, lint,
  build, format:check) en 0.

3. MODELO DE DATOS (tablas reales en BD)
================================================================================

  users                id, role_id → roles, email UNIQUE, password_hash,
                       full_name, active, timestamps + triggers de auditoría
  roles                4 filas: admin_rrhh, analista_seleccion, lider_area,
                       superusuario (rol IT con TODO el poder de admin_rrhh
                       más la gestión exclusiva de usuarios)
  requerimientos       codigo UNIQUE + code_check (REQ-YYYY-NNN); checks:
                       numero_plazas, salario_min, salario_max,
                       salario_rango (min <= max) y rechazo (motivo
                       obligatorio al rechazar)
  codigo_sequences     (anio, ultimo) — generador ATÓMICO del código
                       (SELECT … FOR UPDATE); prohibido MAX(numero)+1
  candidatos           cedula_cifrada (CHECK v1:…), cedula_hash (CHECK
                       ^[0-9a-f]{64}$, UNIQUE), telefono_cifrada, email
                       UNIQUE parcial; nombres, apellidos, ciudad,
                       cargo_actual, expectativa_salarial, disponibilidad,
                       notas. Cédula duplicada → 409 en la API (traduce 23505)
  archivos_cv           candidato_id, original/stored name, mime derivado de
                       magic bytes (pdf|doc|docx|rtf), size, sha256, subido_por
  postulaciones        fase ENUM fase_postulacion (preseleccion,
                       antecedentes, entrevistas, proveedor_externo,
                       contratacion — el ORDEN del enum es la base de la
                       adyacencia) · estado ENUM estado_postulacion (activa,
                       contratado, descartado) · UNIQUE(candidato_id,
                       requerimiento_id) · CHECK postulaciones_contratacion_check
                       (estado='contratado' ⟺ fase='contratacion') · CHECK
                       postulaciones_descarte_check (motivo obligatorio y
                       exclusivo del descarte) · triggers de auditoría
  departamentos        (migración 009) nombre UNIQUE, coordinador, timestamps;
                       8 filas sembradas LARCO (ABASTECIMIENTO, CONTABILIDAD,
                       GESTION HUMANA, OFERTAS, PREVENCION SST, PROYECTOS,
                       SERVICIOS, SISTEMAS)
  entrevistas          (migración 009) postulacion_id → postulaciones,
                       fecha, tipo, notas, estado ENUM estado_entrevista
                       (agendada, realizada, cancelada)
  audit_log            id, table_name, record_id, action (INSERT/UPDATE/DELETE),
                       old_data, new_data, changed_by → users (ON DELETE

                       audit_log_no_mutation rechaza UPDATE/DELETE. La función
                       audit_fila() (v004) prioriza el GUC
                       app.current_user_id que fija la API con el sub del JWT.

4. MÁQUINAS DE ESTADOS
================================================================================

  Requerimiento — POST /api/requerimientos/:id/transiciones
  body {destino, motivo?, resultado?}; destino ∈ {aprobado, rechazado,
  en_proceso, cerrado} (pendiente nunca es destino). La puerta @Roles deja
  pasar a los 4 roles; la MATRIZ de permisos vive en requerimientos-flujo.ts
  (en cada transición de admin_rrhh participa también superusuario, que
  hereda su poder):

    pendiente → aprobado    : solo admin_rrhh (y superusuario)
    pendiente → rechazado   : admin_rrhh (cualquiera) y lider_area SOLO si
                              es el creador
    aprobado  → en_proceso  : admin_rrhh, superusuario y analista_seleccion
    en_proceso → cerrado    : solo admin_rrhh (y superusuario)
    combinación inválida    : 409 · motivo obligatorio en rechazado Y en
                              cerrado (Etapa 9) · en cerrado además
                              RESULTADO obligatorio ∈ {contratacion,
                              cierre_vacante} (400 en la API + CHECK
                              requerimientos_cierre_check)

  'exitoso' es un estado terminal SOLO AUTOMÁTICO: la API lo pone ella
  misma cuando se cubren todas las plazas con candidatos 'contratado'
  (no es destino de ninguna transición manual). «Contrato exitoso».

  Editar (PATCH /:id): solo creador o admin_rrhh y SOLO en estado pendiente
  (409 en otro estado). Los estados de postulación/lectura no se escriben con
  PATCH genérico de estado: el cliente SIEMPRE llama /transiciones.

  Embudo (postulaciones) — dos acciones de escritura:

    POST /api/postulaciones           {candidatoId, requerimientoId}
        roles: analista_seleccion, admin_rrhh · nace en preseleccion/activa
        · 409 si el requerimiento no está en_proceso, si ya existe la fila
        o si el cupo de plazas ya está cubierto (Etapa 9)
    PATCH /api/postulaciones/:id/fase {fase}
        roles: analista_seleccion, admin_rrhh · SOLO AVANZA UN PASO
        (Etapa 9: NO hay retroceso — antes era ±1 y reversible) · 409 si es
        terminal (contratado/descartado), si la fase es la misma, si hay
        salto o si se intenta RETROCEDER («El embudo solo avanza: ...») ·
        409 si el destino es contratacion con TODAS las plazas cubiertas ·
        fase=contratacion ⇒ estado=contratado (terminal) · al cubrir todas
        las plazas, el requerimiento pasa solo a estado 'exitoso'
    POST /api/postulaciones/:id/descarte {motivo}
        roles: analista_seleccion, admin_rrhh · desde cualquier fase NO
        terminal · motivo obligatorio: 400 si viene vacío o solo espacios
        (el servicio recorta) · la UI exige además mínimo 5 caracteres en
        su diálogo · estado=descartado (terminal; la fila se queda en su
        fase actual; NO se pinta en el tablero)

6. SEGURIDAD
================================================================================

  • Contraseñas: scrypt nativo N=16384, r=8, p=1, formato
    scrypt$16384$8$1$salt_b64$hash_b64 (verificado en la tabla users).
    OJO: PowerShell interpola $16384 en cadenas dobles — generar hashes con
    un .js temporal, no con comillas dobles.
  • JWT: HS256, TTL 24 h (JWT_TTL_HOURS=24), payload {sub, email, role} +
    iat/exp y jti de emisión; un payload sin esos 3 campos (p. ej.
    {sub, rol, ver}) → 401. Sin claim de versión ni revocación por usuario.
    La web guarda {token, usuario} en localStorage (decisión MVP documentada
    en store/sesion.ts).
  • RBAC: AuthGuard global + RolesGuard (@Roles) + comprobaciones de
    servicio (creador-o-admin, matriz de transiciones). 4 roles;
    superusuario hereda TODO lo de admin_rrhh y es el único que pasa el
    guard de /usuarios. La web (lib/rbac.ts) solo decide QUÉ BOTONES se
    muestran: el 403 del servidor es la verdad.
  • PII: AES-256-CBC con IV aleatorio por registro (prefijo v1:) para cédula
    y teléfono; HMAC-SHA256 (hash hex de 64 caracteres) para búsqueda exacta
    de cédula SIN descifrar; historiales enmascarados (***); nunca PII en
    claro en listados ni logs. Verificado en BD: solo cedula_cifrada +
    cedula_hash.
  • Rate limit: global 100/min por IP; login 5/min por IP (429 «Demasiadas
    peticiones»). helmet + CORS endurecido.
  • Auditoría por TRIGGERS en BD (audit_fila + audit_log inmutable); la
    changed_by se llena con el GUC app.current_user_id que fija la API dentro
    de la transacción. No se puede desactivar desde la aplicación.
  • Bitácora (Etapa 9): GET /api/historial/auditoria EXCLUSIVA de
    superusuario (@Roles('superusuario')); el resto — incluido admin_rrhh —
    recibe 403. La web oculta el enlace para los demás y redirige la URL
    escrita a mano. Los valores de PII llegan ENMASCARADOS.
  • Importación (Etapa 9): ≤50 PDFs por lote y ≤5 MB por archivo, solo
    application/pdf validado; la cédula es opcional SOLO en este DTO (el
    alta manual sigue exigiéndola).
  • Validación de entorno (zod, al arrancar): JWT_SECRET ≥32 caracteres,
    CRYPTO_KEY_* = exactamente 32 bytes en base64, JWT_TTL 1–72 h. La app
    NO arranca si algo falta.
